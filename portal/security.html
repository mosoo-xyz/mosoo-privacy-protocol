Cryptographic Invariants &
Smart Contract Hardening.

Zero-knowledge systems cannot afford ambiguity. In our architecture, mathematical proofs replace human trust. Here is a comprehensive technical breakdown of our threat models, circuit constraints, and smart contract invariants.

The Cryptographic Foundation

🔢

BN254 Pairing Curve

Mosoo uses the alt_bn128 (BN254) elliptic curve. It features native EVM precompile support (addresses 0x06, 0x07, and 0x08), allowing fast on-chain proof verification without excessive gas overhead.

Order: 21888242871839275222...
⚙️

PoseidonT3 Hasher

Unlike Keccak-256 (which requires ~25,000 constraints per hash in ZK circuits), the Poseidon hash is designed natively over algebraic fields. It executes in just 240 constraints, enabling sub-3-second client proving in web browsers.

ZK-Friendly Algebraic S-Boxes
🔐

Nullifier Determinism

Every note possesses a secret spending salt. When unshielded, the circuit derives a deterministic public nullifier: Poseidon(SecretSalt, LeafIndex). Double-spending is mathematically prohibited by on-chain mapping.

Strict 1-to-1 Note Nullification

Smart Contract Invariants & Defenses

The MosooPrivacyPool contract incorporates five specific defensive safeguards against known vulnerabilities that affected legacy privacy protocols:

🛡️

1. Scalar Field Overflow Boundary Checks

If a user submits an element larger than the BN254 scalar field prime (FIELD_SIZE), integer aliasing can occur where two different values represent the exact same curve point.

Every input in Mosoo enforces:
require(uint256(commitment) < FIELD_SIZE, "Mosoo: commitment outside field");

Defends against field-wrapping attacks
🔒

2. Reentrancy Lock & State Pre-Update

All external withdrawal functions adhere strictly to the Checks-Effects-Interactions pattern. The nullifier hash is marked spent in contract storage (nullifierHashes[nullifierHash] = true) before any ETH/ABEY tokens are transferred to the recipient or relayer.

nonReentrant modifier on all entrypoints
⚡

3. Historical Root Ring Buffer (64 Slots)

On public blockchains, network latency means multiple deposits can happen while you are generating your proof. If the pool only checked the current root, your transaction would revert. Our ring buffer stores the 64 most recent roots, guaranteeing your valid proof succeeds even during high network congestion.

Race-condition proof validation buffer
💎

4. Pool Solvency & Transact Fee Protection

In private-to-private transactions (transact), no funds leave the pool. If a relayer fee is paid, that fee must NOT be taken from the pool's collective balance (which would cause undercollateralization).

The contract strictly requires attached native gas:
require(msg.value >= fee, "transact fee must be attached via msg.value");

Guarantees 100% pool solvency at all times
